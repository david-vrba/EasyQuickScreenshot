# v0.10.1 + v0.11.0 plan — startup lag, edits that land on the last shape, screen recording

**Status 2026-09-29: all three shipped** — v0.10.1 (lag + last-shape edits) and v0.11.0
(recording). Where the build left the plan, it says so below in *Built:* notes.

David, 2026-09-29. Three asks in one message, planned together because they touch the same
files. Shipped in two releases so the small fixes are not held hostage by the big one.

## What David asked for, in his words

1. **Lag.** "Whenever I press Ctrl+Alt+Q… it always quite lags for one second and then it
   shows… the crosshair." His machine was at 90% RAM; everything else felt fast, so the app
   is the thing that degrades first.
2. **Edits land on the last shape.** "When I then press the option to fill it, it doesn't
   fill it, it will fill the next rectangle… I want to fill the last rectangle drawn… and the
   next rectangle as well. The same should work for… selecting color, even selecting the size
   of the text — dynamic update."
3. **Screen recording on Ctrl+Alt+E.** He needed one three times this week. PowerToys'
   ZoomIt (Ctrl+5) records the whole screen with no boundaries and no editing. Wanted: set
   the region, then trim, mute or change the volume, and crop. Save the same way as a
   screenshot — `Q` for the temp file, `E` for a keeper — into a folder of its own. Audio:
   system sound (his answer to the one question asked).

## Measurements that decided the design

Taken on his machine under his load (90% RAM, 6400x1440 desktop), `eqs --time-startup`:

| phase | cost |
|---|---|
| BitBlt of the whole desktop from the screen DC | 87–95 ms |
| GetDIBits into a `Vec` | 13–16 ms |
| copying that `Vec` into the overlay's DIB | 7–10 ms |
| first full-frame blit | 12–18 ms |
| **headless total** | **~120–140 ms** |
| same grab, blitted straight into a DIB section | 83 ms |

So the measurable startup is ~130 ms, not a second. The rest happens where a headless probe
cannot see: window creation, the first present, or the system itself stalling under memory
pressure. That is why a real-use timing log is part of the fix — the next measurement comes
from his own hotkey presses.

GDI per-frame cost at recording sizes: **1280x720 17.7 ms · 1920x1080 29.4 ms · 2560x1440
42.1 ms**. At 1440p that caps recording at 24 fps while burning a core, so the recorder cannot
use the screenshot's capture path.

## Part 1 — startup (v0.10.1)

1. Grab straight into a DIB section and hand that same bitmap to the overlay. Removes the
   `GetDIBits` conversion, the second full-size copy and 74 MB of allocation per capture —
   the allocations are what a machine at 90% RAM pays for most.
2. While dragging, repaint only what moved (the two guide lines, the old and new selection
   border) instead of recomposing and blitting all 37 MB on every mouse move.
3. Start GDI+ when the app starts rather than on the first drawing of the first capture.
4. Timing log: `eqs-timing.log` next to the exe, the last 50 captures, each phase in ms.
   Written after the overlay closes, so it costs the capture nothing. Config `timing_log`,
   off by default, on in David's config.
5. `--time-startup` stays as the headless probe.

## Part 2 — edits land on the last shape (v0.10.1)

- **"Last shape" = the end of the shape list**, derived every time, never stored as an index.
  A stored index is what crashed v0.6.0 when undo removed the shape it pointed at.
- `F` flips fill for what comes next **and** fills or unfills the last shape if it is a
  rectangle or circle. Pressing it after an arrow changes only what comes next.
- A colour (`1`–`8` or a swatch) recolours the last shape and what comes next.
- The wheel changes the last shape's stroke width, or its text size, and what comes next.
- Each of those is one undo step, and a burst of wheel ticks is one step, not twenty.
- While text is being typed, the same changes go to that text.

## Part 3 — screen recording (v0.11.0)

**Flow.** `Ctrl+Alt+E` → the same crosshair overlay → drag the region → recording starts. A
small REC bar (red dot, timer, Stop) sits beside the region and never appears in the video.
`Ctrl+Alt+E` again, or Stop, ends it → the editor opens → `Q` writes `videos/temp.mp4`
(overwritten each time), `E` writes `videos/saved/<timestamp>.mp4`. `Esc` throws it away.

**Capture — DXGI Desktop Duplication.** GPU-side, only when the screen changes, a few ms a
frame. The frame is copied region-only to a staging texture, mapped, and the cursor drawn in.
v1 records one monitor: a region is clipped to the monitor its centre is on.

**Encode — Media Foundation.** `IMFSinkWriter` to MP4: H.264 through the hardware encoder
(NVENC on the RTX 3080) and AAC audio. Built into Windows — no new dependency, no ffmpeg.

**Audio — WASAPI loopback** of the default output device, requested as 48 kHz stereo.
Loopback delivers nothing while nothing plays, so silence is written for the gap from the
clock; otherwise audio would drift ahead of the video every time a sound stopped.

**Stop bar.** `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` keeps it and the region
frame out of the recording. The screenshot overlay gets the same flag, so a screenshot taken
mid-recording does not land in the video either.

**Threads.** Recording is the first thing in the core that outlives a hotkey press, so it
runs on its own thread: capture + encode on one, audio on another, both stopped through one
flag. The screenshot path stays single-threaded and untouched.

*Built:* exactly this, plus the saved video is put on the clipboard as a file (CF_HDROP),
the same way a screenshot's pixels are.

**Editor — in the settings app window.** WebView2 already plays MP4, so the preview, the
timeline and the crop box are HTML. Trim = two handles on the timeline. Crop = a box dragged
over the video. Audio = mute + a volume slider (0–200%). Export runs in Rust through Media
Foundation: no edits means the raw file is moved, which is instant; any edit re-encodes. If
`eqs-settings.exe` is missing, the recording is saved as is.

**Folders and keys.** `videos/` and `videos/saved/` beside `shots/`. `Ctrl+Shift+Alt+V` opens
the videos folder (David left the choice to me: V for videos), plus a tray item.

**Config.** `record_hotkey = "ctrl+alt+e"`, `videos_dir = "videos"`, `record_fps = 30`,
`record_audio = "system"` (or `"none"`), `videos_folder_hotkey = "ctrl+shift+alt+v"`.
`save_hotkey` stays readable so old configs load (`deny_unknown_fields`), and is ignored.

**Not in v1, on purpose:** microphone (a later switch), a region spanning two monitors,
pause/resume, GIF export.

## Verification, without driving his running app

- Unit tests for every pure part: last-shape edits and their undo, the silence-gap
  arithmetic, region-to-monitor clipping, crop rounding to even sizes, trim bounds.
- `eqs --record-test X Y W H SECONDS out.mp4`: a headless recording, checked with `ffprobe`
  for duration, frame rate, size and an AAC stream.
- The export tested the same way: trim + crop + volume on a known file, then `ffprobe`.
- `--time-startup` before and after Part 1.
